# Identity Prism OS — Full Audit (2026-08-16)

Scope: live production (`www.vedanshusrivastava.com` / `memory-wugweb.vercel.app`) + full source read of `/Users/abcom/Documents/GitHub/memory`. Every finding below was verified against either live API responses (`curl`) or the actual source code — nothing here is guessed from static page fetches (that method was tried first and threw false positives, see note at the end).

## The one bug that explains almost everything

**The entire L1→L2→L2.5 processing pipeline never runs, in production, ever.**

`src/lib/memory/scheduler.ts` is where the embedding worker, L2 signal processing, and L2.5 semantic-graph processing live. It's built on `node-cron` — `cron.schedule('*/1 * * * *', ...)` etc., called at module load time. Two fatal problems:

1. **Nothing imports this file.** Grepped the entire `src` tree for `memory/scheduler` — zero references. It is dead code. Its `cron.schedule()` calls never execute even once.
2. **Even if something imported it, it still wouldn't work.** `node-cron` needs a long-running Node process to keep its in-memory timers alive. Vercel serverless functions are spun up per-request and frozen/killed right after — in-process timers never fire there. This entire approach is incompatible with the hosting model described in your own `CLAUDE.md` (`Deployed on Vercel`).

The only actual scheduled job in the app is the one Vercel Cron in `vercel.json`:
```json
{ "path": "/api/jobs/run", "schedule": "0 3 * * *" }
```
And `/api/jobs/run` doesn't call the embedding worker, `ProcessingEngine`, or `SemanticEngine` either — it only runs `runSourceSync`, `runScheduledPublisher`, `runPublishingQueueJob`, `runRetryWorker`, `runRetentionCleanup`.

**Proof, from live data:** `GET /api/memory/stats` → `{"total_packets":34,"embedding_stats":{"pending":34,"processing":0,"embedded":0,"failed":0}}`. Every single memory packet, including ones promoted weeks ago, is stuck at `embedding_status: pending` and `processing_status: pending`. 0 have ever been embedded. 0 have ever been processed.

**This single dead file is why:**
- Buffer → Promote puts real rows in `memoryPacket` (confirmed working), but nothing downstream ever reflects it — matches "I promoted, I see no change anywhere."
- `/api/processing/signals`, `/topics`, `/intelligence`, `/entities`, `/semantic` all filter on `processing_state: 'complete'`, which no packet ever reaches → L2 Signals and L2.5 Semantic graph are permanently empty.
- Cognitive `buildContext()` pulls L1+L2+L2.5+L4 — with L2/L2.5 always empty, every Decide/Evaluate/Gaps call reasons over near-nothing → explains "all 4 tabs is almost the same stuff" (generic output because there's no real signal to differentiate on).
- `/ask`'s RAG retrieval (`src/lib/memory/rag.ts` → pgvector cosine search) has nothing embedded to search → answers are always ungrounded even when the LLM call itself works.
- Persona traits/evolution timeline stay empty ("No traits yet") — persona evolution reacts to processed signals that never arrive.

**Fix:** replace `node-cron` with real Vercel Cron entries hitting dedicated routes, e.g. `/api/jobs/embed`, `/api/jobs/process-l2`, `/api/jobs/process-l25`, each calling the existing `processEmbedding` / `ProcessingEngine.processPacket` / `SemanticEngine.processSemantic` functions in a batch loop (the logic in `scheduler.ts` is fine, it just needs to run from an HTTP-triggered route, not an in-process timer). Note Vercel Hobby-plan cron only supports daily granularity — sub-minute processing needs Pro, or an external trigger (cron-job.org / QStash) hitting the route every 1–2 min. Then backfill: run it once manually against the 34 stuck packets.

## Confirmed bugs (each independently verified)

### 1. `entities.processing_state` column missing in production DB — P1
`GET /api/health/system` → HTTP 500: `Invalid prisma.entity.groupBy() invocation: The column entities.processing_state does not exist in the current database.` `schema.prisma` defines the column (`src/lib/health/system.ts:32`), no migration in `prisma/postgres/migrations/` ever added it to Neon. Classic schema/DB drift — `docs/PROJECT_TRACKER.md` marks the related bug (BUG-005) "Fixed" but this half clearly wasn't deployed.

**Direct consequence:** the Console's L0/L1/L2 tiles read this exact endpoint (`src/app/console/page.tsx` → `useLayerHealth()`); a 500 makes the fetch reject, caught by `.catch(() => 'Offline')`. **This is why L0 Intake / L1 Memory / L2 Processing show "Offline"** — it's a false negative from one broken query, not the actual layers being down.

**Fix:** `npx prisma migrate dev --name add_entity_processing_state` against a dev DB, commit the migration, `npx prisma migrate deploy` to prod. Run `prisma migrate status` first — worth checking for other drifted columns given this one slipped through.

### 2. `/ask` chat is broken — confirmed live, P1
Posting a correctly-shaped message to `/api/chat` returns a stream that errors immediately: `{"type":"error","errorText":"An error occurred."}`. The AI SDK swallows the real cause, but `src/app/api/chat/route.ts` tries, in order: `AI_GATEWAY_*` → `GROQ_API_KEY` → `OPENAI_API_KEY` (default model `gpt-4-turbo`). Given `CLAUDE.local.md` already notes the OpenAI key hit a 429/quota wall elsewhere in the app, that's the most likely culprit here too, but it needs a Vercel log check to confirm which of the three providers is actually configured and failing.

**Fix:** check Vercel function logs for the real thrown error (search `CRITICAL_RAG_FAILURE`); most likely rotate/verify `OPENAI_API_KEY` or set `GROQ_API_KEY` (has a generous free tier, already coded as a fallback).

### 3. Public profile page performance / SSR — not a bug, false alarm retracted
Earlier in this session I flagged `/p/system_user` as "blank" and `/system` as "stuck loading" using a static (non-JS) fetch tool. That tool can't execute client-side React, so any `"use client"` page looks broken whether it is or not. Verified directly: `/api/profile/system_user` returns full real data, `/api/system/features` returns real data. Both retracted in Notion. Lesson: don't trust raw-HTML fetch for CSR page health again — this write-up is grounded in live API calls and source reads instead.

## Page-by-page findings

**Integrations (`/integrations`)** — Not broken, but "add new integration type" doesn't exist as a feature. The connector list (`src/lib/ingestion/connectors/registry.ts`) is a hardcoded array — GitHub, YouTube, Blog RSS, Notion, Google Drive/Calendar, LinkedIn/X/Behance/Dribbble placeholders. Adding a new source means writing a new `Connector` object in code and redeploying; there's no UI or API for user-defined connectors. Worth deciding whether that's in scope — if yes it's a real feature build, not a fix.

**Buffer → Memory** — Promote works correctly at the data layer (verified: 34 real packets in `memoryPacket`, correctly tagged, correctly deduped by hash). The "no change anywhere" perception is 100% the dead scheduler above, not the promote code itself.

**History (`/history`)** — Genuinely, correctly empty. `GET /api/output/history` → `[]`. Nothing has ever been generated + published through Output Studio, so there's nothing to show. Not a bug — it's an honest empty state. Once `/content` → Compose → Generate → Publish is used, this will populate.

**Content (`/content`)** — Not a stub, it's a real 3-tab feature (Compose / Live / Drafts) with generate → draft → schedule/publish → live-profile-sync all wired to real endpoints. It *looks* like a stub because Compose's only entry point is a bare "Decision ID" text field — you're expected to already have a cognitive decision UUID to paste in. There's a dropdown of recent decisions, but it only appears if you've generated cognitive decisions already, and even then defaults to blank. First-time UX genuinely looks empty/broken. **Recommended fix:** default-select the most recent decision, or let Generate work from freeform input directly without requiring a decision ID first.

**Cognitive (`/cognitive`)** — 4 real, structurally different tabs (Decide / Evaluate / Gaps / History) — different inputs, different result shapes. They *feel* the same because of the root-cause bug: every mode's context comes from `buildContext()` pulling L1+L2+L2.5, and L2/L2.5 are always empty, so the LLM has almost nothing differentiated to reason over regardless of which tab you're in. Fixing the scheduler should directly fix this.

**Persona (`/persona`)** — Not a stub; real sections (Communication Profile, Behavioral Traits, Evolution Timeline, Adaptive UX, Feedback) all wired to real endpoints. Two issues: (a) Communication/Writing/Decision style render as raw `<pre>{JSON.stringify(...)}</pre>` dumps instead of designed UI — reads like a debug page, which is likely why it feels like a stub; (b) Traits/Evolution Timeline are empty for the same root-cause reason (persona evolution reacts to processed signals that never arrive).

**Career (`/career`)** — UI/UX pass:
- Three distinct concerns stacked on one page with no visual separation — career-tree editor, `JobPipeline`, `JobSearchAgent` — reads as three different tools glued together rather than one coherent page.
- Add/Edit form uses placeholder text as the only label (no `<label>` elements) — an accessibility anti-pattern (placeholder disappears on focus, not read consistently by all screen readers, no persistent field context).
- "Industries" is a raw comma-separated text input — error-prone, no chip/tag input, no autocomplete against existing values.
- No date validation/sorting — "Dates" is a free-text string (e.g. "2020 — Present"), so career-tree ordering is whatever order items were added in, not chronological.
- No empty/loading skeleton differentiation from other pages — consistent with the rest of the app, so at least it's not inconsistent, just plain.

**Admin (`/admin`)** — Original user-reported "Application error: a client-side exception" is still unconfirmed on my end — Chrome extension isn't connected in this session, so I couldn't reproduce it live. Code review shows the health-check `Promise.all` wraps each fetch in try/catch and treats HTTP 500 as valid JSON (`BROKEN` status), so it shouldn't crash the page even with bug #1 active — meaning this is likely a *separate*, still-open issue. **Next step:** open `/admin` logged in, DevTools → Console, send me the actual red error text — that's the fastest way to close this one.
